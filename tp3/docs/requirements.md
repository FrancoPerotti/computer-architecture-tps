# TP3 — Especificación de requisitos

## 1. Convenciones

- Cada requisito tiene un identificador estable.
- **Tipo** distingue su origen:
  - **Explicit**: obligación expresada directamente por la consigna.
  - **Derived**: comportamiento necesario para cumplir una obligación o la semántica del ISA.
  - **Engineering**: requisito interno adoptado para robustez, calidad o verificabilidad.
- **Fuente** indica la sección de `consigna.md`, la referencia normativa del ISA u otro requisito del que proviene.
- **Decisión de origen** identifica la decisión de diseño aprobada que generó el requisito; se utiliza `—` cuando el requisito no surge de una decisión interna.
- **Aceptación** describe evidencia observable; los nombres definitivos de los tests se establecerán en el plan de verificación.
- Estos requisitos expresan **qué** debe cumplir el sistema. Las decisiones sobre **cómo** implementarlo se registran aparte.
- Algunos requisitos de CPU son capacidades de alto nivel y actúan como requisitos padre; los requisitos ISA, de inmediatos, control, hazards y memorias detallan y verifican esas capacidades sin necesidad de multiplicar artificialmente la cantidad de requisitos.

### Referencia normativa del ISA

En este documento, **RISC-V ISA** significa el subconjunto requerido de **RV32I**, con semántica y codificación basadas en **RISC-V User-Level ISA V2.2**.

## 3. Conjunto de instrucciones

Para cada requisito ISA, la aceptación mínima consiste en ejecutar casos nominales y de frontera, comparar registros, memoria y PC contra la referencia normativa aplicable y comprobar que no haya efectos laterales indebidos. La consigna define **qué instrucciones RV32I** son obligatorias y el estándar RISC-V define **su semántica y codificación exactas**; las instrucciones custom del proyecto se rigen por sus decisiones aprobadas.
